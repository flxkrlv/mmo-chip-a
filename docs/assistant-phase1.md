# Read-only LLM Circuit Assistant — Phase 1

## Purpose

The assistant is a **read-only, LLM-driven netlist analyst**. It sends the current extracted circuit snapshot to the configured server-side model and asks the model to identify plausible functional fragments. It never writes annotations, renames nets, changes the generated netlist, creates a device record, or changes any project file at runtime.

The assistant deliberately contains **no hard-coded circuit-function matcher**. It does not decide that two BJT devices are a differential pair, or that a transistor pair is a mirror, through a fixed pattern rule. Functional hypotheses are generated by the LLM from the complete extracted circuit data and the user's analysis brief.

## Data sent to the LLM

For an `All die` request, the model receives the complete browser-side extraction snapshot. For `Analyze selected`, it receives the explicitly selected extracted device set. The payload contains each device's immutable UUID and instance name, device kind and model, terminal-to-net mapping, available geometry parameters, named nets, global-rail markers, extraction/netlist warnings, scope and user brief.

| Data | Purpose in model analysis |
|---|---|
| Device instances and terminal mapping | Lets the model follow possible signal, bias and feedback paths rather than rely on visual proximity. |
| MOS/BJT/passive geometry | Provides W/L, area, multiplier and resistance information when extraction produced it. |
| Named nets and global-rail markers | Lets the model distinguish a local net from a shared supply/ground connection. |
| Existing warnings | Supplies the same practical extraction quality warnings the application already exposes. |
| User brief | Makes the investigation specific, for example `LM2937, BJT LDO; look for Widlar/bandgap reference, error amplifier, feedback divider, current sources and protections.` |

## User workflow

Open **Die Viewer → AI**, fill the optional **Analysis brief**, then select **Run full-netlist LLM analysis** and choose **Find analog subcircuits**. The analysis result contains Russian prose under **LLM full-netlist analysis**. This narrative is retained even when the model chooses not to produce a selectable subcircuit.

The model may optionally append a ` ```json ` block with hypotheses. A JSON hypothesis becomes an interactive card only after the local validator confirms that every cited instance name exists and that all cited devices form a connected graph through at least one non-global net. This means `Show on die`, `Net Graph`, `Netlist` and `Show schematic fragment` always refer to a real fragment in the present extraction snapshot.

The browser persists analysis brief fields, the checkbox state, the last response and the active finding separately for each die. The personal analysis workspace survives navigation to schematic/graph and page reload; it is not written into the shared project annotations. Credentials and full netlist text are never stored in this browser state.

## Minimal local validation

> The local validator is a **reference and connectivity check**, not a circuit classifier.

A model hypothesis is rejected when it names a missing device, consists of only one non-protection device, or connects its claimed devices solely via a global rail such as `GND`, `VSS`, `VDD`, `VCC`, `VIN`, `VOUT`, `AVDD` or `AVSS`. A single rail-connected diode/zener protection candidate is allowed. The check does not prove a circuit function, calculate its parameters, or raise model confidence.

## Model response handling

The model is allowed to return ordinary Russian Markdown prose. A prose-only answer is successful and appears in the UI; it no longer fails with a JSON parse error. A ` ```json ` code block is parsed only to create interactive fragment cards.

The server-side request timeout defaults to **120 seconds** for full-netlist analysis. It can be changed without source edits through `ASSISTANT_LLM_TIMEOUT_MS`, constrained to 10–300 seconds. The UI reports the measured backend request duration. A local timeout message includes the configured duration so it can be distinguished from an HTTP/provider error.

## Server configuration

Use only backend process environment variables. Never place an API key in TypeScript, JSON, a committed `.env` file or browser storage.

```powershell
$env:OPENROUTER_API_KEY = "<your-key>"
$env:ASSISTANT_LLM_TIMEOUT_MS = "120000"
npm run dev -w backend
```

Generic settings are also supported:

```text
ASSISTANT_LLM_API_KEY
ASSISTANT_LLM_BASE_URL
ASSISTANT_LLM_MODEL
ASSISTANT_LLM_TIMEOUT_MS
```

## Validation completed

The test suite covers an LLM-only preparation response with zero hard-coded findings, Markdown prose plus optional JSON, rejection of a GND-only pseudo-pair, rejection of a nonexistent/disconnected device reference and the request-size guard. A real request to the locally configured model was also completed successfully during implementation: it returned a narrative and two locally validated selectable hypotheses in approximately 35 seconds.

Run standard validation from the repository root:

```text
npm run build
npm test
```

## Explicit limitations

LLM-generated results are engineering hypotheses. A candidate labelled `bandgap`, `Widlar`, `error amplifier`, `current source` or `protection network` is not electrical proof. Confirmation requires reviewing the shown fragment, checking extraction correctness, tracing the surrounding path and—when models are available—simulation or measurement. The assistant must surface uncertainty rather than infer a functional block from a global rail or a part-number description alone.

## Netlist problems mode

The AI panel also provides **Find netlist problems & errors**. With no user brief, the LLM performs an open-ended anomaly review. With a brief, it uses the brief as the investigation focus while still receiving the full graph and all supplied extraction/netlist warnings. The prompt is not a fixed checklist: floating terminals, isolated fragments, implausible emitter/collector paths, base-only groups, asymmetry, missing matches, suspicious shorts and apparently unreachable devices are examples of questions, not an exhaustive rule list.

This mode uses the same structured hypothesis schema. Each accepted item is displayed as a red `netlist_problem` card and can be opened on die, in Net Graph, as a netlist fragment or as a schematic fragment. The card must include a suspected issue, the affected instances/nets, why it may be a real problem, what could make it intentional, and next checks. A finding is not treated as proof of a silicon or extraction error.

The model prompt now asks for the compact JSON block **first**, followed by a separate Russian explanation. The server parses JSON from the entire response before truncating the narrative, so a long explanation cannot hide a valid structured block later in the response. A prose-only response remains available in the collapsed narrative section, but selectable cards require valid, locally referential JSON hypotheses.
