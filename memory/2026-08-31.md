# 2026-08-31 — LLM token-ladder / timeout fix

## Problem
Full-graph analysis on `glm-5.3-flash` (opencode.ai/zen/go/v1) was
cut off: first ladder rung `maxTokens=8000` was entirely consumed by
`reasoning_content` (CoT), `finish_reason=length`, `content` empty,
then the 16000 retry was aborted by the fixed 300s per-attempt timeout.

Root cause: OpenAI-compatible API does not split reasoning vs answer
budget — CoT and the JSON answer share one `max_tokens`. First rung (8k)
too small, per-attempt timeout too short for a reasoning model.

## Fix (Variants A + diagnostics)
- `llmGraphAnalysis.ts`: ladder `[8000,16000,32000]` → `[16000,32000,64000]`.
- New `attemptTimeoutMs(maxTokens, baseMs)`: scales per-attempt timeout
  proportionally to budget (ref 8000 tokens = `ASSISTANT_LLM_TIMEOUT_MS`,
  default 300s): 16k=600s, 32k=1200s, 64k=1800s (cap
  `MAX_ATTEMPT_TIMEOUT_MS=1_800_000`). Applied to analyze
  stream+nonStream and discuss (16000 fixed, both paths).
- `describeEmptyBody`: logs full length of `reasoning_content` (was only
  first 80 chars) so CoT burn is visible in logs.
- Frontend DiscussPopup hard client abort 300s → 1_800_000s (was aborting
  before the backend could answer). Analyze stream path already has no
  client timeout.
- Docs `assistant-phase1.md`: rewritten timeout paragraph.

## Decisions
- Do NOT restrict reasoning (no dedicated CoT-off / reasoning_effort caps) —
  user wants high-quality analysis, just not infinite. Cap exists via
  ladder end (3 real attempts) + 30-min per-attempt ceiling.

## Tested
- `tsc --noEmit` clean in backend and frontend.
- Backend `npm test`: 27/28 pass; the single fail (`app.test.ts` "analyses a
  supplied circuit snapshot") is pre-existing on HEAD f36c055 (depends on a live
  LLM reply), not caused by these changes.
- Live finding (2026-08-31): glm-5.3-flash burned 15995/16000 output tokens on
  reasoning_content and was cut by the wall-clock timeout right as content

## 2026-08-31 seventh pass — clarifying questions for analysis

Idea (user): a reasoning model that buries itself in re-verification of
ambiguous data (VCC_1 / GND_1 / ref / floating taps) might benefit from being
able to ASK the user instead of looping. Added optional clarification rounds.

- Types (shared): `AssistantClarificationMode = "off"|"auto"|"always"`; request
  gets `clarificationMode`, `clarificationAnswers`; `AssistantLlmState` gets
  `questionSet?`, `needClarification?`; stream event `questions`.
- Backend prompt (`promptForGraphAnalysis`): model may return `{"questions":[]}`
  (≤4) depending on mode; on the second pass answers are appended as
  authoritative-but-not-overriding context, prompt forbids asking again.
- `analyseFullGraphWithLlm(…, clarification)`: if the first pass returns
  `questions` (and mode != off, no answers yet) → `onEvent("questions")` +
  result with `llm.needClarification`/`questionSet`, NO cards. Second pass with
  `clarificationAnswers` suppresses stray questions (anti-loop).
- API `/analyze[/stream]`: probes mode/answers, forwards `questions` event.
- Frontend: global preference `assistantClarificationMode` (default auto,
  persisted); mode select in the Prompt & settings area; numbered questions UI
  with a single textarea + "Send answers & continue" / "Continue without
  answering"; re-runs `analyseAssistantCircuitStream` with answers, scope
  remembered via `lastRunScope` ref.
- `tsc --noEmit` clean backend+frontend; backend tests 27/28 (the 1 fail is the
  pre-existing live-LLM `app.test.ts` case).

Follow-up: deepseek-v4-flash ignored "always" and returned cards — the prompt had
an escape hatch ("if no real questions, return empty questions and proceed").
Closed it: for `always` the prompt now mandates NON-EMPTY questions (producing
cards forbidden), may ask about key devices/blocks/priorities; returning empty
`questions` is prohibited. `auto` stays soft. No backend fallback (per user).

Also: cardUpdate prompt made TOOL-FIRST. `cardUpdateRules` now requires calling
`mmochip_card_update` with `{reply, cardUpdate}` as the ONLY reliable way (JSON
fallback only if provider exposes no tools); removed "Respond with the SINGLE
JSON object", "Do not wrap in fences", repointed systemPrompt line 859 to the
tool. (Prompt-only change; backend tool loop already treats card_update as
terminal and `useTools=true` always.)

## 2026-08-31 sixth pass — silence/heartbeat visibility for "GUI freezes mid-stream"

Symptom: while deepseek-v4-flash/glm think, the GUI appeared frozen on the last
paragraph and the backend console stayed silent — looked like a hang. Root cause
has two parts:
1. Reasoning models stream `reasoning_content` in bursts with tens-of-seconds
   gaps; there was no heartbeat and no backend liveness logging.
2. The idle timer was being re-armed on ANY received byte. SSE keepalive
   comments / blank lines from a gateway that never delivers actual tokens would
   reset the timer forever → stream could hang silently with no abort.

Fixes:
- `llmStream.ts`: idle timer (`armIdleTimer`) is now re-armed ONLY on real data
  `[DONE]` / content / reasoning_content / tool_calls. keepalive/blank lines do
  NOT extend it → a silent upstream now aborts after ASSISTANT_LLM_STREAM_IDLE_MS
  (15 min) instead of hanging forever.
- `llmStream.ts`: a `setInterval` prints a waiting progress line every 15s while
  no token arrives: `[llm-stream] waiting… silent=N s (chunks=…, content=…, reasoning=…)`
  → operator can tell "model quietly thinking" from "upstream is dead".
- SSE endpoints (`assistant.ts` analyze/stream + discuss/stream): heartbeat event
  every 10s while the LLM runs, so the connection stays visibly alive.
- Frontend: `AssistantStreamEvent.type` + "heartbeat"; analyze loading UI now
  shows a pulsing dot + "last chunk Ns ago" (re-armed every 1s while loading),
  dot turns red when idle > 60s. New `mmpulse` keyframes in global.css.

## 2026-08-31 fifth pass — reasoning-loop prompt (glm-5.3-flash)

Evidence: `LLM stream done in 908991ms (maxTokens=32000)` then
`empty content finish_reason=length` — GLM-5.3-flash used ALL 32k output tokens
on `reasoning_content` (repeatedly "let me finalize 5 cards… let me reconsider…"
loops) and never reached the JSON `content`. NOT a timeout/abort — stream ended
normally with length. deepseek-v4-flash on the same die finishes (thinking=100k
chars, content=4.5k chars, 5 findings) because it "closes" reasoning. Escalating
to 64k/128k would only extend the same loop.

Fix (user-approved phrasing): added "CONFIDENCE OVER PERFECTION" block to
`promptForGraphAnalysis` (analyze system prompt) telling the model the netlist
may be incomplete/error-prone, 100% accuracy is NOT required, commit on FIRST
pass, uncertainty -> low-confidence card + missingEvidence (refinable later via
LVS/vision), and that exhausting the token budget means no answer at all.
- User explicitly declined a reasoning-loop guardrail that would stop escalation
  32k→64k→128k; for complex netlists extra budget is acceptable if it's stable.
- `tsc --noEmit` clean afterwards; not yet live-tested against glm-5.3-flash.

## Idle-based timeouts + bigger token ladder (2026-08-31, third pass)

Trigger: glm-5.3-flash hit Output 16000 / Reasoning 15995, killed by wall-clock
timeout exactly when the JSON answer started; another wasted & burned run.

Fixes:
- `llmStream.ts`: `timeoutMs` is now an IDLE timeout. `armIdleTimer()` resets on
  every received chunk (content / reasoning / tool_calls / any body byte); the
  request aborts only when the provider is silent for `timeoutMs` (default 300s).
  No wall-clock cap on total elapsed time for streams.
- analyze `streamAttempt`: passes base `timeoutMs` (not `attemptTimeoutMs`) as
  idle; discuss `callLlm` stream call likewise. Non-stream `doFetch` paths keep
  `attemptTimeoutMs` (wall-clock, scaled by maxTokens, cap 30 min).
- Token ladder up: analyze `[32000, 64000, 128000]` (was off-by-reasoning 8k/16k),
  discuss `max_tokens: 32000` (both stream + non-stream).
- Frontend DiscussPopup hardTimeout is now idle: `armHardTimeout()` re-arms on
  every token/thinking/tool event; abort only after 1_800_000ms of silence.
- `docs/assistant-phase1.md` timeout paragraph rewritten (idle vs wall-clock).

## 2026-08-31 fourth pass — stream idle 900s + retries + salvage

CNM log evidence (three distinct failure modes traced):
1. `This operation was aborted` — OUR idle timer fired (provider silence > cap).
2. `terminated` — GATEWAY closed the connection mid-stream after ~877s while
   reasoning flowed (14478 reasoning tokens + ~1610 content tokens already in);
   NOT our timeout. `fetch failed` follows when the gateway is temporarily down.
3. GLM habitually burns 14-16k tokens on CoT, making requests very long.

Implemented:
- `llmStreamIdleMs()`: `ASSISTANT_LLM_STREAM_IDLE_MS`, default 900_000 (15 min),
  clamp 30s–1h; separate from `ASSISTANT_LLM_TIMEOUT_MS`. Used for analyze
  `streamAttempt` (was `timeoutMs`) and discuss `callLlm` stream.
- Idle-abort in analyze loop now escalates to the NEXT token rung with a fresh
  stream (`continue`) instead of falling back to non-streaming (which would face
  the same provider pauses). Hard errors (HTTP, gateway down) still fall back to
  one non-stream attempt. `isClientAbortError` shared from llmStream.
- `streamAttempt` salvages a partially-received stream: if the dropped stream
  already produced a valid JSON payload (`parseModelReply().payload`), it is
  accepted (`salvaged: true`) instead of throwing the run away.
- `llmStream.ts`: `isClientAbortError`, `isRetryableStreamError` (retry on
  terminated / fetch failed / ECONNRESET / TLS / 429; NOT client aborts); stream
  mid-loss diagnostic logs elapsed + chunks + content/reasoning lengths.
- Non-stream `fetchWithRetries` (analyze) now retries transient network errors
  (abort exceptions rethrown), not only 429.
- Docs updated (idle 900s + env var; salvage + retries behaviour).

## Vision tool + cardUpdate reliability (2026-08-31, second pass)

### Vision tool
- New `overlayLayerListData(snapshot.overlayLayers)` — single source of truth,
  inserted into the *user data* (both JSON and text netlist modes) so every
  model sees the `AVAILABLE OVERLAY LAYERS` block even if it ignores tool descs.
- `overlayLayerNameHint(...)` short human-readable list shared by system prompt
  + VISION_TOOL description. Removed the hardcoded `'Si','sirtl','lm2937_stud'`
  examples; examples/ids are now derived from the live `overlayLayers`.
- Added the layer-naming convention hint in the system prompt and tool schema:
  metal layers "me1/metal 1…", diffusion "diffusion/si/polysi/poly", developed
  diffusion "hf/sirtl…". Model may ask the user which image a name maps to.
  Metal layer → check terminal connectivity; diffusion layer → compare
  transistor structure.
- `layerName` param now carries an `enum` built from `__base__` + real layer
  ids/names (cap 30). Watch opencode-go handling of enum in tool schemas.
- Frontend `pollVision`: sends back the layer that was ACTUALLY rasterised
  (`resolvedLayerName`: requested→resolved name / top-visible fallback) instead
  of echoing the model's request string. visionTool `executeVisionTool` now
  appends a `Note: requested layer "X" is not available… showing "Y"` line when
  the model asked for an unresolvable layer (`isSameLayer` alias-tolerant).

### cardUpdate via tool (replaces fragile prose parsing)
- New `mmochip_card_update` function tool: `{ reply, cardUpdate }` structured
  args; always offered (independent of LVS/vision checkboxes). `useTools=true`
  so the loop runs even with both visual tools off.
- Tool loop treats card_update as TERMINAL: grabs reply+cardUpdate from args and
  breaks without another LLM call; `buildExtra` always pushes CARD_UPDATE_TOOL.
- Fallback remains: `extractReplyCardUpdate(text)` lifts `{reply, cardUpdate}`
  out of prose / ```json fences (not just `content.startsWith("{")`).
- `cardUpdateRules` prompt hardened: never claim an update in prose without a
  cardUpdate; prefer the tool call; UIs apply only valid cardUpdate objects.
- `sanitizeCardUpdate`: accepts string → [string] for add/remove UUIDs, numeric
  string / number for net ids, so partial/wrong-typed model args don't drop.
- Frontend shows "📋 mmochip_card_update — preparing card update…" on tool_start.
